# Project rules

- Reuse the app’s existing interface and shared components for new screens. Use the same shared card/list-row builder for library and store results; show the active sort metric in the shared right-hand badge. Keep search above list pills, result counts inside the search field, and sort/order actions in the existing overflow menu and sort dialog. Do not introduce separate control layouts or unsolicited informational copy, status labels, implementation details, or explanatory banners (such as “offline snapshot”). Add visible text only when it is needed for a user action or a meaningful empty/error state.

- Refreshes must preserve usable data and artwork while checking for updates. Apply additions, removals, and changes incrementally; do not clear shared caches or blank existing UI as part of a routine refresh. Keep displayed artwork until replacement artwork is ready, including when a request fails. Pull-to-refresh should give only a brief visual acknowledgement; dismiss the spinner promptly and finish work quietly in the background without a persistent refreshing banner.
- Never expose a game card without a real, verified local image and its decoded handle already ready for layout. This applies to startup, swipe transitions, scrolling, and refresh, across every store and list. No controller placeholders, blank cards, tiny colour previews, image fades, or bind-time file/network work. Unprepared games must stay discoverable in a separate preparation view with retry/artwork-selection actions. Keep shared asset policy in `assets/`; views express demand and consume publications.
- For every change, consider its impact across the app. Trace related callers, data sources, and UI flows, and update all applicable areas rather than fixing only the screen where the issue was noticed. Put shared behavior in common components and verify affected paths. For example, Steam artwork URL handling should be consistent everywhere artwork is loaded, including the library, wishlist, and game details.
- Preserve native RecyclerView/GridLayoutManager scroll distance, fling momentum, and nested scrolling. Never return zero/partial consumption to wait for artwork or replay scroll deltas later. Prefetch local handles ahead of the viewport, and keep vertical gestures from turning into pager swipes. Device verification must assert scroll progress and touch direction as well as absence of placeholders.
- Keep verification proportional to the change. Use focused checks for small UI adjustments; do not run the full connected-phone navigation/scrolling suite by default. Reserve broad device regressions for changes that affect those flows, and avoid repeating passed checks without a relevant new change or failure.
- Prefer standard Android navigation and UI patterns. Follow familiar platform conventions for back navigation, app bars, contextual selection actions, menus, dialogs, and controls; use custom behavior only when the task calls for it. Apply these patterns consistently with the app's shared visual components.
- Do not implement backward compatibility, data migrations, or fallbacks for obsolete app formats. Implement only the current app data model and format.
- Keep all content modals visually consistent: use the shared `ContentDialog` in `app/src/main/java/com/gamefibre/ContentDialog.kt` and `NativeUi` widgets for headings, text, inputs, and buttons. Use `ContentDialog.setActions` for fixed footer actions and its optional title for the shared close button. Preserve its theme-aware background, 28dp rounded corners, spacing, font, scrolling body, and keyboard handling. Do not introduce separate `AlertDialog`/`MaterialAlertDialogBuilder` styling or custom modal palettes. Apply shared modal design changes in these common components. Fullscreen media viewers and the navigation drawer use their dedicated layouts.

- Website copy: use plain, human language for an adult reader. State what a feature does directly, with short headings and usually one short sentence per feature. Keep descriptions brief; add a concrete example only when it helps explain a use. Avoid marketing slogans, hype, filler, clever metaphors, and AI-style phrasing such as “Big covers, no clutter,” “find your next adventure,” or “before you commit an evening to it.” Prefer familiar names and natural phrasing, including “Epic” instead of “Epic Games” in website prose.
